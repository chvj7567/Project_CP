# 언어 설정 클라우드 덮어쓰기 버그 수정 — 정책/UX 점검

## § 헤더

- **목표**: GPGS 로그인 시 클라우드의 `languageType`이 로컬(기기/설정) 언어를 덮어쓰는 버그를 막는 수정에 대해, "언어 = 기기 로컬 전용" 정책이 플레이어 경험상 타당한지와 엣지 케이스를 점검한다.
- **검증 가설**: "언어를 기기 로컬 전용 설정으로 두고 클라우드 로드를 무시해도, 멀티 디바이스 사용자가 혼란 없이 각 기기에서 기대한 언어를 본다."
- **현재 단계 범위 적합성**: 범위 내. CatPang Beta 단계의 "리텐션 루프 안정화" 에 포함되는 데이터 동기화/UX 버그 수정이다. 신규 메커니즘·신규 콘텐츠가 아니라 기존 동작 교정이므로 도메인 수치·밸런스는 없다.
- **핵심 메커니즘**: 언어는 신규 유저 첫 실행 시 기기 언어로 1회 결정되고, 이후 옵션(UISetting)에서만 변경되며 로컬에 영속 저장된다. GPGS 클라우드 병합 시 `languageType`만 로컬 값으로 보존(클라우드 값 무시)하여 로그인이 언어를 바꾸지 못하게 한다. 클라우드 저장 자체는 유지(로드만 무시).

> 본 문서는 spec의 결정 락(언어=로컬 전용, 클라우드 로드 무시, 저장은 유지)을 **전제로** 정책 타당성과 엣지만 점검한다. 결정 락은 뒤집지 않는다.

## 1. 정책 타당성 점검 — "언어 = 기기 로컬 전용, 멀티 디바이스 시 기기마다 독립 언어"

### 1.1 정책 요약

| 항목 | 정책 |
|---|---|
| 언어 결정 권한 | 기기 로컬 1곳 — 신규 유저 첫 실행(기기 언어) + 옵션 변경 |
| 클라우드 동기화 | 언어는 **동기화하지 않음** (저장은 되나 로드 시 무시) |
| 멀티 디바이스 | 기기마다 독립. 기기 A의 언어 변경이 기기 B에 전파되지 않음 |
| 언어 종류 | Korea / English 2종 (`Defines.ELanguageType`). 비한국어 기기는 English로 매핑 |

### 1.2 모바일 게임 관례 대비 합리성

언어 설정의 동기화 정책은 업계에서 **두 갈래**로 갈린다. 본 점검의 결론은 "CatPang 규모/구조에서는 기기 로컬 전용이 합리적"이다.

| 관례 | 채택 게임 성향 | CatPang 적용 시 |
|---|---|---|
| **기기 로컬 전용** (본 정책) | 캐주얼/퍼즐, 계정이 가벼운 게임. 언어를 OS·기기 설정의 연장으로 봄 | 적합 — 아래 근거 |
| 계정(클라우드) 동기화 | 대형 RPG/MMO, 계정 비중이 큰 게임. 언어를 계정 프로필 속성으로 봄 | 과함 — 2종 언어, 데이터 충돌 비용 |

**기기 로컬 전용이 CatPang에 합리적인 근거:**

1. **OS 언어 일치 기대가 강한 장르다.** 매치-3 캐주얼 퍼즐 유저는 "이 기기에서 보던 언어"를 기대한다. 한국어 기기를 새로 켰는데 다른 기기에서 설정한 영어가 나오면 오히려 위화감이 크다. 언어는 "계정 속성"보다 "기기/OS 설정"에 가깝게 인식된다.
2. **언어 종류가 2종(Korea/English)뿐이다.** 동기화로 얻는 편익(여러 기기에서 동일 언어 자동 적용)이 작다. 어느 기기든 옵션에서 1탭이면 원하는 언어로 바꿀 수 있어, 동기화 부재로 인한 사용자 비용이 낮다.
3. **데이터 충돌 비용을 없앤다.** 언어를 클라우드 병합 대상에 넣으면 "어느 기기의 마지막 변경이 진실인가"를 판정해야 한다(타임스탬프/우선순위 규칙 필요). 2종 언어를 위해 그 복잡도를 떠안는 것은 비용 대비 효익이 낮다. 로컬 전용은 이 판정 자체를 제거한다.
4. **수정 폭이 최소다.** 기존 영속성(로컬 저장)·표시 경로는 그대로 두고 클라우드 로드 한 줄만 무시하면 된다. 회귀 위험이 가장 작은 해법이다.

### 1.3 반례 / 우려 (명시)

정책을 뒤집을 정도는 아니나, 기록해 둘 우려는 다음과 같다.

- **우려 U1 — 기종 변경(기기 교체) 시 언어 재설정 1회 필요.** 한국 유저가 영어로 바꿔 쓰다가 새 기기(한국어 기기)로 갈아타면, 새 기기는 한국어로 시작한다. 영어를 원하면 옵션에서 1회 다시 바꿔야 한다.
  - 영향도: 낮음. 기기 교체는 드문 이벤트이고, 새 기기 기기언어 = 유저의 기본 선호일 가능성이 높다(한국어 기기를 쓰는 유저는 대개 한국어 OK). 옵션 변경은 1탭. **정책 유지 권장.**
- **우려 U2 — 멀티 디바이스 동시 사용자에게 "한쪽에서 바꾼 언어가 다른 쪽에 안 옴".** 이는 버그가 아니라 의도된 동작(요구사항 ②④와 일치)이지만, 일부 유저는 "설정이 동기화 안 된다"고 느낄 수 있다.
  - 영향도: 낮음. 캐주얼 퍼즐 멀티 디바이스 동시 사용자 비중이 작고, 각 기기에서 독립적으로 원하는 언어를 보는 것이 오히려 자연스럽다. **정책 유지 권장.**

> 위 우려는 모두 "옵션에서 1탭 변경"으로 해소되며, 동기화 도입의 복잡도·충돌 비용을 정당화하지 못한다. **결론: 정책 타당.** (1.4 결론 참조)

### 1.4 결론

언어 = 기기 로컬 전용 정책은 CatPang(캐주얼 매치-3, 2종 언어, GPGS 단일 슬롯 클라우드 저장) 맥락에서 **타당하다.** 업계 캐주얼/퍼즐 관례에 부합하며, 동기화로 얻는 편익보다 충돌 판정 비용 제거·회귀 최소화의 이득이 크다. 발견한 반례(U1·U2)는 모두 영향도 낮음이며 옵션 1탭으로 해소 가능하다.

## 2. 엣지 케이스 점검

코드 동작을 추적해 각 케이스의 기대 결과와 실제 보장 여부를 확인했다. 추적 근거 파일:
- 부팅 로컬 로드 선행: `Assets/Scripts/Scenes/ResourceDownload.cs:38` (`LoadLocalData`)
- GPGS 로그인 클라우드 로드: `Assets/Scripts/Lobby/LBLoginHandler.cs:43` (`LoadCloudData`)
- 병합 가드/보존: `Assets/Scripts/Manager/CHMData.cs` `LoadCloudData` 병합 루프
- 신규 유저 기기언어: `Assets/Scripts/Manager/CHMData.cs:44`, `:301`
- 옵션 변경: `Assets/Scripts/UI/UISetting.cs:52,64`
- 표시: `Assets/Scripts/Manager/CHMString.cs:34`

### E1 — 기기 A 영어 변경 → 기기 B(한국어 기기) 동일 계정 로그인 → B는 한국어 유지?

- **기대(요구사항)**: B는 한국어 유지.
- **실제 보장**: 보장됨.
  - 기기 B 부팅 시 `LoadLocalData` 선행 → B는 신규 로컬(파일 없음)이면 기기언어(한국어)를, 기존 로컬이면 B에 저장된 언어를 `loginLocalDataDic`에 채운다.
  - 이후 GPGS 로그인 → `LoadCloudData`가 클라우드(영어)를 가져오나, 병합 루프에서 `cloudLogin.languageType = localLogin.languageType`로 로컬(한국어) 보존.
  - 결과: B는 한국어 유지. **요구사항 충족 — 확인 완료.**

### E2 — 옵션 변경 직후 SaveData로 클라우드에 언어가 올라가도, 로드 시 무시되므로 문제없는가?

- **기대**: 클라우드에 영어가 저장돼 있어도 다음 로그인/로드에서 그 값이 적용되지 않아야 함.
- **실제 보장**: 보장됨.
  - 옵션에서 영어로 변경 → `UISetting`이 `loginData.languageType = English` 후 `SaveData` → 클라우드/로컬 모두 영어 저장(저장은 유지가 결정 락).
  - 이후 어떤 기기에서든 `LoadCloudData` 시 병합 루프가 `languageType`을 그 기기의 로컬 값으로 덮으므로, 클라우드에 올라간 영어는 **로드 시 무시**된다.
  - "저장은 무해, 로드만 무시" 결정과 일치. **문제없음 — 확인 완료.**
  - 추가 메모: 같은 기기에서 영어로 바꾼 뒤 같은 기기에서 재로그인하면, 그 기기의 로컬도 영어이므로 영어 유지(자기 자신을 보존). 정상.

### E3 — 신규 유저가 GPGS로 바로 로그인하는 첫 실행 시 언어 순서 문제 없는가?

- **기대**: 기기언어 적용 → 로그인 순서로, 로그인이 언어를 깨지 않아야 함.
- **실제 보장**: 보장됨 (순서가 구조적으로 고정).
  - 부팅 순서상 `ResourceDownload.cs:38 LoadLocalData`가 **항상 먼저** 실행된다. 신규 유저는 로컬 파일이 없어 `data.Item1==true` 경로(`CHMData.cs:44`)로 기기언어가 `loginLocalDataDic`에 채워진다.
  - 그 다음 로비에서 GPGS 로그인 → `LoadCloudData` 실행. 이때 로컬 키는 이미 존재하므로 병합 루프의 가드(`TryGetValue == false → continue`)에 걸리지 않고, `languageType` 보존 라인이 실행된다.
  - 결과: 신규 유저 첫 GPGS 로그인에서도 기기언어 유지. **순서 문제 없음 — 확인 완료.**
  - 주의(잠재 의존성, 회귀 감시용): 본 보장은 "LoadLocalData가 LoadCloudData보다 항상 선행"한다는 부팅 순서에 의존한다. 만약 향후 로컬 로드 없이 클라우드 로드만 단독 호출하는 경로가 생기면 병합 가드의 `continue`로 보존 라인이 건너뛰어질 수 있다. 현재 코드에는 그런 경로가 없으므로 문제없으나, 이 순서 의존성을 회귀 테스트에 고정할 것을 권장(§3 합격 조건 C5).

### E4 (추가 발견) — 비한국어 기기의 언어 매핑

- 코드상 기기언어 판정은 `Application.systemLanguage == Korean ? Korea : English`다(`CHMData.cs:44,301`). 즉 한국어 외 모든 기기(일본어·중국어 등)는 English로 시작한다.
- 본 수정 범위 밖이며 기존 동작이다. 2종 언어(Korea/English) 정책의 의도된 결과이므로 본 버그 수정에서 변경하지 않는다. (언어 종류 추가는 spec §7 범위 밖.)
- 점검 결과: 본 버그 수정과 무관하며 정책 일관성 유지. **변경 불요.**

## 3. 검증 기준 (스모크) — 기획/QA 관점 합격 조건

spec §6 스모크 4항목을 사용자 시나리오로 풀어 합격 조건으로 명시한다. 각 조건은 "한 줄로 합격/불합격 판정 가능"하도록 기대 결과를 단정한다.

| ID | 시나리오 | 조작 | 합격 조건 (기대 결과) |
|---|---|---|---|
| C1 | 버그 재현/수정 확인 | 클라우드에 영어가 저장된 계정을 한국어 기기에서 GPGS 로그인 | 로그인 직후 및 이후 모든 화면이 **한국어**로 표시 (로그인으로 언어 안 바뀜) |
| C2 | 옵션 변경 영속 | 옵션에서 영어로 변경 → 앱 완전 종료 후 재실행 | 재실행 시 **영어**로 시작 |
| C3 | 옵션 변경 + 재로그인 불변 | C2 직후 상태에서 GPGS 재로그인 | 재로그인 후에도 **영어** 유지 (클라우드 값이 덮지 않음) |
| C4 | 신규 유저 첫 실행 | 로컬 데이터 없는 신규 유저로 첫 실행(로그인 전/후 모두) | 기기언어 기준 — 한국어 기기는 **한국어**, 그 외 기기는 **영어**로 시작. 첫 GPGS 로그인이 이를 바꾸지 않음 |
| C5 | 회귀 — 일일 미션 병합 | 클라우드/로컬 간 `lastDailyResetDateKey` 날짜 차이가 있는 계정으로 로그인 | 일일 미션 충돌 병합(날짜 비교 로컬 우선)이 **기존과 동일**하게 동작 + 언어는 로컬 보존 (두 보존이 서로 간섭 없음) |

**합격 판정 룰**: C1~C5 전부 합격해야 통과. 하나라도 불합격이면 game-designer/gameplay-programmer로 반려.

> 멀티 디바이스 독립성(E1)은 C1과 본질적으로 같은 경로(클라우드 영어 → 로컬 보존)를 검증하므로 별도 항목으로 두지 않고 C1에 포섭한다. 단, QA가 실제 2기기로 재현 가능하면 C1을 2기기 시나리오(기기 A 영어 변경 → 기기 B 로그인 → B 한국어 유지)로 확장 실행할 것을 권장.

## 4. 구현 요청사항 (gameplay-programmer 용)

본 작업은 기존 동작 교정 버그 수정으로, **신규 도메인 산출물(Enum/Interface/에셋/SO)이 없다.** 구현 명세는 spec §4 및 plan Task 1에 단일 진실로 존재한다.

- **Enum**: 추가 없음. (`Defines.ELanguageType` 기존 사용, 변경 없음)
- **Interface**: 추가 없음.
- **에셋 키**: 추가 없음.
- **SO 스키마 / 수치 필드**: 추가 없음. (`Data.Login.languageType` 기존 필드, 변경 없음)
- **변경 지점**: `Assets/Scripts/Manager/CHMData.cs` `LoadCloudData` 병합 루프 1줄 추가 (plan Task 1) — 본 기획서가 새로 지정하는 코드 변경 없음. 정책/검증 관점만 보강.

## 5. 범위 밖 (YAGNI) — spec §7 승계

- languageType 클라우드 저장 제거 (불필요, 변경폭만 커짐 — 저장은 무해, 로드만 무시로 충족)
- 언어 종류 추가 (Korea/English 외)
- UISetting UI/UX 변경
- 언어 클라우드 동기화(계정 단위 언어) 도입 — §1.4 결론상 미채택
