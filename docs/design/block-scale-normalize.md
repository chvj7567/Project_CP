# 블럭 비율 정규화 (9×9 풋프린트 고정) — 기획서

## § 헤더

- **목표**: 보드 크기(`boardSize`, 정사각, 실제 운용 3~9)가 9×9보다 작아도 보드 전체가 9×9와 동일한 화면 가로 풋프린트를 채우도록, 블럭 1개당 크기·간격을 `factor = 9 / boardSize` 배 확대한다. 9×9는 factor=1.0(기존과 완전 동일).
- **검증 가설**: 작은 보드에서 블럭이 커지면 화면 빈 여백 없이 보드가 꽉 차 가독성·터치 정확도가 올라가고, 9×9 회귀가 없다.
- **현재 단계 범위 적합성**: 범위 내. 프로토타입(start-develop-simple) 레이아웃 개선. spec/plan 결정 락(9×9 풋프린트 고정, `factor = 9/boardSize`, 정사각 전제)을 그대로 따르며 그 안에서 UX·시각만 보강한다.
- **핵심 메커니즘**: 레이아웃 단일 진실 지점(`CHInstantiateButton`)에서 셀 width/height(+margin)에 factor를 곱하면 간격·히트판정·낙하거리·배치좌표가 일괄 추종한다. 블럭 `localScale`과 스폰 트윈 목표를 factor로 맞춘다. 수치 밸런스(점수·시간·이동·HP) 변경 없음 — 순수 레이아웃.

## § 1. 플레이어 경험 효과

현재 동작 기준 사실 (코드 확인):
- 9×9에서 origin 프리팹은 `localScale = 1`이고 9칸이 화면 가로 풋프린트를 채운다. 즉 **"9×9 한 칸 크기"가 현재의 기준 셀 크기**다.
- 작은 보드(예: 3×3)도 같은 origin 셀 크기로 배치되므로, 지금은 **화면 가운데에 작은 보드만 덩그러니 놓이고 좌우·하단에 넓은 빈 여백**이 생긴다. (x 중앙 정렬만 되어 있어 보드가 작을수록 차지 면적이 작다.)

본 변경의 효과:
1. **빈 화면 제거 / 시각적 균형** — 작은 보드도 9×9가 차지하던 가로 영역을 꽉 채워, 스테이지 간 보드 위치·크기가 일관된다. 초반 저보드(3~5) 스테이지가 "미완성처럼 휑한" 인상을 주지 않는다.
2. **가독성 향상** — 셀이 커지므로 고양이 스프라이트·장애물 블럭(Wall/CatBox/Fish 등) 식별이 쉬워진다. 초반 스테이지는 튜토리얼·신규 유저 구간이라 가독성 이득이 특히 크다 (group 1~2가 3×3, 보드 분포상 초반 = 저보드).
3. **터치 정확도 향상** — 드래그 히트 판정 반경이 `buttonWidth / 2f`로 factor에 비례해 커진다. 셀이 커지면 인접 스왑 오탭이 줄어 매치-3 핵심 조작 만족도가 오른다.
4. **9×9 무변화** — factor=1.0이므로 대다수 후반 스테이지(아래 §3 분포 참조)의 플레이 감각은 그대로 유지된다.

## § 2. 시각 / 가독성 리스크 점검

### 2.1 결론: 실질 리스크 낮음 (관리 가능)

spec/plan의 결정 락을 유지한 채로도 **추가 cap이나 하한 가정 없이 진행 가능**하다고 판단한다. 근거는 아래 세 축 점검 결과다. (단, 한 가지 조건부 권고는 §2.5 참조)

### 2.2 스프라이트 확대 흐려짐(블러)·픽셀화

- 우려: factor 최대 4.5배(2×2)면 스프라이트를 4.5배 확대 → 텍스처 해상도 부족 시 블러/픽셀화.
- **실제 데이터상 2×2는 존재하지 않는다** (§3 참조). 실 운용 최소 boardSize는 **3** → 최대 factor는 **3.0**. 사양이 가정한 2×2(4.5배)는 발생하지 않으므로 최악 배율은 3.0으로 낮아진다.
- 판정: 고양이/블럭 스프라이트는 셀 단위 아트(원본 해상도가 화면 1칸보다 충분히 크게 임포트된 형태)라 3배 확대에서 눈에 띄는 픽셀화는 낮다. 다만 3배는 비자명한 확대이므로 **스모크 시 3×3 스테이지(group 1 stage1/2)에서 실제 화면 블러 육안 확인**을 합격 조건에 포함한다 (§4).

### 2.3 safe area 초과 여부

- 우려: 셀이 커지면 보드가 화면/노치 safe area를 넘어 잘릴 수 있다.
- 핵심: 본 기능은 **"9×9 풋프린트"를 상한으로 고정**한다. 작은 보드를 키워도 그 결과 폭은 정확히 9×9가 이미 차지하던 폭과 같다 (`factor × boardSize × 셀 = 9 × 셀`). 즉 **확대 후 풋프린트가 현재 9×9 스테이지보다 커지지 않는다.** 9×9가 이미 safe area 안에서 정상 표시되고 있으므로(현행 출시 가정), 작은 보드의 확대 결과도 같은 한도 안에 들어온다.
- 세로(y): spec 결정대로 y는 top 기준 유지. 가로폭이 9×9와 동일하고 셀이 정사각이므로 세로 점유 높이도 9×9 한도를 넘지 않는다.
- 판정: **safe area 초과 리스크 없음** (9×9 풋프린트가 상한이라는 구조적 보장).

### 2.4 고양이 스프라이트 비율 왜곡

- 우려: width와 height에 다른 배율이 들어가면 블럭이 찌그러진다.
- 점검: 정사각 보드 전제(`horizontalCount == verticalCount == boardSize`)이고 factor는 단일 스칼라다. `localScale = Vector3.one * factor`로 x·y 동일 배율이 적용된다. width·height 모두 같은 factor를 곱하므로 **종횡비 보존**.
- 판정: **비율 왜곡 없음** (단일 스칼라 균등 확대). 단, 비정사각 보드는 spec §6에서 범위 밖으로 락되어 있으므로 본 보장은 정사각 전제 위에서만 성립 — 비정사각 보드가 추후 도입되면 이 절을 재검토해야 한다(현재 데이터에 비정사각 없음).

### 2.5 조건부 권고 (디자인 결정 — 채택안 명시)

- 검토 대안 A: **cap 도입** — factor 상한(예: 3.0)을 둬 미래에 2×2 같은 극소 보드가 추가돼도 4.5배 블러를 막는다. trade-off: cap에 걸린 보드는 9×9 풋프린트를 다 못 채워 좌우 여백이 다시 생긴다(기능 목적 일부 후퇴) + spec 결정 락(풋프린트 고정)과 충돌.
- 검토 대안 B: **cap 없이 진행** — 현 데이터 최소 3×3(3.0배)이라 cap 불필요. trade-off: 미래에 누군가 Stage.json에 2×2를 넣으면 4.5배 확대가 무방비.
- **채택: 대안 B (cap 없이 진행).** 이유: (1) 현 데이터에 2×2 없음, (2) cap은 spec 결정 락(풋프린트 고정)과 정면 충돌, (3) 프로토타입 범위에서 미발생 케이스 방어는 YAGNI. 대신 미래 대비로 **"운용 boardSize 하한 = 3" 을 본 기획서의 명시 가정으로 기록**한다 — boardSize 2를 신규 스테이지에 넣을 경우 본 기능의 시각 검증을 재실시해야 한다(주석/메모 수준, 코드 가드 불필요).

## § 3. 실제 운용 boardSize 분포

`Assets/AssetBundleResources/json/Stage.json` 전 250행의 `boardSize` 값을 집계했다.

| boardSize | factor (=9/n) | 스테이지 수 | 비고 |
|---|---|---|---|
| 3 | 3.00 | 3 | group 1 stage1·2(튜토리얼) + 1건 |
| 4 | 2.25 | 1 | |
| 5 | 1.80 | 16 | |
| 6 | 1.50 | 10 | |
| 7 | 1.29 | 30 | |
| 8 | 1.13 | 24 | |
| 9 | 1.00 | 166 | factor=1.0, 변화 없음 |
| **합계** | — | **250** | |

검산: 3 + 1 + 16 + 10 + 30 + 24 + 166 = 250 (Stage.json 행 수와 일치).

해석:
- **9×9 외 보드가 실제로 다수 존재한다** — 84 / 250 행(약 33.6%)이 9 미만. 본 기능은 사문화 기능이 아니라 1/3가량의 스테이지 행에 실제 영향을 준다.
- 영향 행 중 **factor가 큰(=시각 변화가 큰) 저보드는 소수** — boardSize 3·4는 합쳐 4행뿐이고 나머지(5~8, 80행)는 factor 1.13~1.80의 온건한 확대다.
- **실 운용 최소 boardSize = 3** → 최대 factor = 3.0. spec이 예로 든 2×2(factor 4.5)는 데이터에 없다 → §2.2 블러 최악 배율을 3.0으로 낮춘다.
- 참고: Stage.json 행 수 250 = 노멀/하드 공유 150 + 보스 100 (CLAUDE.md). 노멀 모드는 하드 데이터를 boardSize 그대로 재사용(시간제거·이동2배만 적용)하므로 boardSize 분포는 모드 무관 동일.

## § 4. 검증 기준 (스모크 — 디자이너 합격 조건)

spec §5 / plan Task 3을 디자이너 관점 합격 조건으로 구체화한다.

| # | 케이스 | 합격 조건 |
|---|---|---|
| 1 | **9×9 스테이지** (예: 후반 group) | factor=1.0. 블럭 크기·간격·x중앙정렬·낙하·드래그가 변경 전과 **픽셀 단위로 동일** (회귀 0). |
| 2 | **3×3 스테이지** (group 1 stage 1) | 보드가 9×9와 동일한 가로 폭을 꽉 채운다(좌우 빈 여백이 9×9와 동일 수준). 셀이 약 3배 커진다. 좌우·상단이 safe area 안에 들어온다. |
| 3 | **블러 육안 확인** (3×3, 최대 factor 3.0) | 확대된 고양이/장애물 스프라이트에 거슬리는 블러·픽셀 계단이 **없다**. (있으면 텍스처 임포트 해상도 상향 별도 과제로 분리.) |
| 4 | **비율 왜곡** (3×3·5×5) | 고양이 스프라이트가 가로/세로로 찌그러지지 않는다(정사각 셀, 종횡비 보존). |
| 5 | **드래그 히트 판정** (작은 보드) | 커진 셀에서 인접 스왑 시 의도한 블럭이 잡힌다. 오탭으로 엉뚱한 칸이 선택되지 않는다. |
| 6 | **중간 배율** (5×5, factor 1.8 / 7×7, factor 1.29) | 매치 → 특수블럭 생성, 폭탄 발동 범위, 낙하 애니메이션이 정상 위치에서 동작(픽셀 좌표가 row/col 인덱스와 어긋나지 않음). |

> 메트릭 산출이 필요한 항목은 없음(레이아웃 시각 검증). qa-simulator 호출 불필요 — 헤드리스 시뮬은 픽셀 레이아웃·블러를 판정할 수 없으므로 본 기능은 에디터 육안 스모크로 종결한다.

## § 5. 구현 요청사항 (gameplay-programmer 용)

> 구현 단계·시그니처·파일 위치는 plan(`docs/superpowers/plans/2026-06-04-block-scale-normalize.md`)이 단일 진실이다. 본 절은 디자인이 요구하는 결과 계약만 명시한다 — 코드 구조는 plan/programmer 판단.

- **Enum**: 추가 없음 (레이아웃 변경, 신규 에셋 키 없음).
- **Interface**: 추가 없음.
- **에셋 키**: 추가 없음 (기존 origin 블럭 프리팹 재사용).
- **SO 스키마 / 수치 필드**: 신규 없음. 기존 `StageInfo.boardSize`(Stage.json)를 입력으로 그대로 사용.
- **디자인 계약 (결과 기준)**:
  - `factor = 9 / boardSize` (`ReferenceBoardSize = 9`, 정사각 전제). 9×9 → factor 1.0.
  - 확대 후 보드 가로 풋프린트 = 9×9 풋프린트와 동일 (셀·간격 모두 factor 추종 → §2.3 safe area 보장의 전제).
  - x·y에 **동일 단일 배율** 적용 (종횡비 보존 — §2.4).
  - 9×9 스테이지는 변경 전과 픽셀 동일 (회귀 0 — §4 케이스 1).
  - 운용 boardSize 하한 = 3 가정 (cap 없음 — §2.5). boardSize 2 도입 시 본 기획서 재검증 필요.

## § 6. 범위 밖 (YAGNI)

spec §6과 동일 — 비정사각 보드, boardSize > 9(축소), 런타임 동적 리사이즈, 세로 별도 중앙정렬, factor cap 로직. 점수·시간·이동·HP 등 수치 밸런스는 본 기획 대상 아님(레이아웃 한정).
