## 2. 추가 컨텐츠 후보 (권장 1개)

### 후반 스테이지(121~150)에 시간제한 모드 스테이지 보강

- **카테고리**: 스테이지
- **요지**: 그룹 13·15(스테이지 121~130, 141~150)는 100% 이동제한 모드로만 구성되어 있어 시간제한 스테이지가 0개다. 초중반(그룹 1~10)에서 그룹당 평균 6.7개였던 시간제한 스테이지가 완전히 사라지면서, 후반 진입 플레이어가 시간 압박 없이 이동 최적화 전략만 반복하는 단조로운 흐름에 고착된다.
- **점수**: 검증가치/구현비용/플레이어경험/데이터근거 = 4/2/5/5 → 종합 **18**
- **근거**:
  - `Assets/AssetBundleResources/json/Stage.json` — 그룹 13(stage 121~130) 10개, 그룹 15(stage 141~150) 10개 전부 `"time": -1.0`
  - 반면 그룹 1(stage 1~10)은 9개가 `time > 0`
  - `Assets/Scripts/Defines.cs` — `EFailReason.TimeOver` 정의됨, 시간제한 인프라 완비
  - `Assets/Scripts/GamePlay/GPBoard.cs` 등 게임플레이 코드 변경 불필요: Stage.json JSON 수정만으로 시간제한 활성화 가능

#### 유저 플로우

1. **노출 시점·트리거**
   스테이지 선택 화면(UIStageSelect)에서 그룹 13·15에 해당하는 스테이지(예: 125번, 147번)를 선택했을 때, 스테이지 시작 팝업(UIGameStart)에 기존 "이동 N회" 안내 외에 또는 단독으로 "제한 시간 30초"가 표시된다. 잠금 해제 기준(이전 스테이지 클리어)은 변경 없이 기존 그대로 적용된다.

2. **화면 변화**
   GameScene 진입 시 상단 HUD에 타이머 아이콘과 카운트다운이 표시된다. 현재 이동제한 스테이지에는 타이머 UI가 숨겨져 있으므로 `time > 0` 여부에 따른 표시 분기는 이미 구현되어 있다. 이동제한과 시간제한을 동시에 갖는 복합 스테이지(그룹 3의 stage 28 패턴: time=30·moveCount=10 선례 존재)라면 두 HUD 요소가 모두 렌더링된다.

3. **입력 행동**
   플레이어는 평소처럼 블록을 드래그하여 매치를 시도하되, 화면 상단의 타이머가 줄어드는 것을 인식한다. 이동 횟수와 타이머를 동시에 관리하기 위해 더 빠르고 효율적인 매치 결정을 내려야 하며, 연쇄 폭탄(PinkBomb·RainbowPang 등) 활용 동기가 강해진다.

4. **시스템 반응**
   타이머가 0에 도달하면 `EFailReason.TimeOver` 이벤트가 발행되어 UIGameEnd 팝업이 "시간 초과" 메시지와 함께 표시된다. 이동 횟수가 먼저 소진된 경우 `EFailReason.MoveOver`가 우선 발행된다. 복합 조건 스테이지에서는 둘 중 더 빨리 충족되는 조건이 실패 판정에 적용된다.

5. **반복·재발생 패턴**
   해당 스테이지 실패 시 재도전 버튼을 통해 동일 스테이지를 다시 시작한다. 시간제한은 매 도전마다 동일하게 리셋 적용되므로, 플레이어는 "30초 내 최적 매치 경로"를 찾는 반복 학습 루프에 진입한다. 그룹당 2~3개 배치하면 이동제한 스테이지와 시간제한 스테이지가 교차되어 리듬감이 생긴다.

6. **종료·해소 조건**
   `targetScore` 달성 시 `EGameState.GameClear`로 전환된다. 클리어 후 UIGameEnd에 점수·남은 시간(또는 남은 이동 횟수)을 표시하고 다음 스테이지 잠금 해제로 이어진다. 실패 시에는 광고 시청(AdWatch)으로 시간 또는 이동 횟수를 추가(AddTime·AddMove 아이템 활성화)하는 IAP 동선이 자연스럽게 노출된다.

7. **다른 시스템과 상호작용**
   `DailyMissionService.OnStageClear` 트리거는 스테이지 타입과 무관하게 발동되므로 일일 미션(mission 101: NormalStageClear×3)은 자동 카운팅된다. 시간제한 스테이지에서 위기 상황이 빈번해지면 `addTimeItemCount`/`addMoveItemCount`를 소비하는 IAP 아이템(shopID 4, 5)의 후반 활용 맥락이 넓어져 수익화 노출 빈도가 높아진다.

8. **엣지 케이스**
   `targetScore = -1`·`moveCount = -1`인 현재 생존형 스테이지(stage 38·51·53·54·56·61·62·67·68·84·138 패턴)와 혼동되지 않도록, 신규 시간제한 스테이지는 반드시 명시적 `targetScore > 0`을 가져야 한다. 또한 그룹 13·15의 `boardSize`(주로 7~9)와 `blockTypeCount`(5)는 이미 최대치이므로, 30초 내 달성 가능한 `targetScore` 설정을 위해 기존 그룹 8~9(boardSize 5~7) 수준의 레이아웃을 StageBlock.json에서 재참조하거나 새로 설계해야 할 수 있다.

9. **유저 정보·피드백**
   타이머 카운트다운은 그룹 1~10에서 이미 검증된 UI 패턴이므로 후반 진입 플레이어에게도 학습 비용이 낮다. 스테이지 120 이상을 클리어한 플레이어는 이동 최적화에 이미 숙련되어 있기 때문에, 시간제한이 추가되면 "익숙한 전략에 새로운 긴장감이 더해진" 신선함으로 인식될 가능성이 높다. 클리어 시 잔여 시간 표시는 "빠른 클리어" 도전 욕구를 자극하는 추가 피드백이 된다.
